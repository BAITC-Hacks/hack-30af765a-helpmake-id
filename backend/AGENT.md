# Backend Agent Instructions

These instructions apply to all work under `src/`. More specific instructions in
subdirectories override or extend this file.

## Stack and Style

- Python 3.12+, FastAPI, Pydantic v2, SQLAlchemy 2.0 Core, asyncpg, Alembic, pytest.
- Follow the import and formatting style from `pyproject.toml`: single quotes,
  one import per line, 95-character line length.
- Multiline function calls, function signatures, collection literals, imports,
  SQLAlchemy expressions, and Alembic operations must use a trailing comma after
  every item, including the final item. Put the closing delimiter on its own
  line. When an expression must wrap, prefer one argument/item per line instead
  of manually packing several items onto a continuation line.
- Keep short expressions on one line when they fit. Do not add a trailing-comma
  multiline layout merely to make a short call taller. Run Ruff formatting and
  keep its output as the formatting authority.
- Keep code asynchronous where the surrounding code is async. Do not introduce
  blocking database, network, or filesystem calls into request paths.
- Preserve the existing flat JSON response style. Do not introduce a new envelope
  unless the surrounding module already uses one.
- At the API persistence boundary, controllers convert validated Pydantic input
  schemas to primitive dictionaries before calling create/update/upsert model
  functions. Models should not perform request-schema serialization when a
  dictionary is practical. Typed scalar IDs, filters, limits, and operation
  parameters remain ordinary model arguments.
- Updates are full replacements of the resource's mutable persisted fields. Do
  not implement partial-update behavior with `exclude_unset`, `exclude_none`,
  sparse dictionaries, or read/merge/write logic.
- Follow the established main-branch structure: flat async functions, SQLAlchemy
  Core models, thin controllers, and existing response shapes. Do not introduce
  repository, unit-of-work, command-bus, or general application-service
  abstractions unless explicitly approved.
- Declare reusable custom domain and persistence exception classes in the
  relevant `api/models/<domain>.py` module and export them from
  `api/models/__init__.py`. Controllers may raise, catch, and translate these
  model-owned exceptions, but must not declare custom domain exceptions.
- Minimize repetition. Keep one canonical implementation of each business rule
  and persistence operation, update its callers, and remove obsolete branch-only
  implementations. Do not retain compatibility delegates or re-export shims for
  functionality that has not been deployed.

## Tests and Verification

- For structural refactoring, first place one domain's code in the correct layers
  without intentionally changing its public behavior. Once that domain is
  structurally complete, add or update its automated tests before starting the
  next major domain. Schema tests follow the completed table-model and generated
  migration changes.
- The coverage gate is 90% (`tool.coverage.report.fail_under` in `pyproject.toml`).
  Do not lower it.
- For API work, cover schema validation, model/database behavior, controller
  exception mapping, endpoint status codes, and permissions.
- `make test` must run database-backed tests against a fresh disposable database
  built from the complete Alembic chain. Database-backed tests sharing that
  database must stay in one xdist group so parallel workers cannot truncate,
  claim, or mutate each other's rows.
- Use focused pytest targets while developing, then run the relevant broader test
  group before considering the work complete.

## Database and Migrations

- Postgres migrations live under `src/migrations/postgres/versions`.
- SQLAlchemy `Table` definitions are the source of truth for the intended
  application schema. Define every column, type, nullability rule, server
  default, foreign key, unique/check constraint, and index in model metadata
  before generating a migration.
- Distinguish SQLAlchemy `default` from `server_default`: `default` is applied by
  SQLAlchemy when an application statement omits the value, while
  `server_default` is database DDL and must appear in Alembic. Choose explicitly
  and keep any schema-layer default consistent with it.
- Generate schema migrations with `make migration M="<description>"`. Never add
  or change a database field only in a migration.
- Hand-review generated Alembic migrations. Autogenerated output is a starting
  point, but handwritten raw SQL is prohibited. Use SQLAlchemy and Alembic
  operations only; if a required change cannot be represented safely, stop and
  request an explicit design decision.
- Do not add PostgreSQL triggers, stored procedures, or stored functions for
  application rules. Use SQLAlchemy-declared indexes/constraints and guarded
  model statements instead.
- Migrations must be deterministic, explicit about constraints and indexes, and
  safe for existing deployed data.
- Apply generated migrations to a fresh development database and run Alembic's
  schema-drift check. The final metadata must produce no additional operations.
- Every Alembic migration must define `downgrade()` with only `pass`. Do not add
  reverse schema or data operations.
- See `migrations/postgres/CLAUDE.md` for the complete workflow.

## Security and Boundaries

- Validate external input at API boundaries with Pydantic schemas and explicit
  constrained types.
- Never hardcode secrets, credentials, tokens, or environment-specific values.
- Preserve permission checks when changing API code. Superusers (`is_superuser=true`)
  bypass RBAC checks entirely — do not add extra gates for them.
- Do not leak internal exception details through HTTP responses. Controllers
  translate expected domain failures into the existing API error format.
